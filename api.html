API reference · v1

Payments for firms that do deals.

One API for cards, ACH and instant payouts, collected into the same account the deal runs on. A payment intent, a charge, a refund, a payout, an event — with the fee returned on every object, not on an invoice a month later.

Quickstart

POST/v1/payment_intents

Create an intent with an amount in dollars converted to cents, and the rail that should carry it. Every write needs an Idempotency-Key; send the same key on a retry and you get the same object, never a second charge.

Authentication

Every request carries a bearer key. The prefix decides the mode, and the two modes are separate stores — a test key can never read or write a live row.

KeyModeWhat it does
sk_test_…TestRuns every route against the test ledger. No money moves.
sk_live_…LiveAnswers 501 live_mode_unavailable until the partner bank is named. Never send one from a browser.
Live mode is off by design. There is no acquiring partner yet, so a live key is refused rather than silently failing. The same request works in test mode today and settles for real once the route is signed.

Idempotency

Every POST needs an Idempotency-Key header. The first request creates the object; a retry with the same key returns that same object with the same id — so a dropped connection never becomes a second charge.

  • Use a key tied to the business event (order-8841-attempt-1), not to a timestamp.
  • A missing key is 400 idempotency_key_required.
  • A different body with the same key still returns the first object: the key identifies the attempt, not the payload.

Test mode

Test mode is a real ledger of test rows: objects persist for the life of the process, fees are computed for real, events fire and webhooks deliver. What it does not do is move money or hold a card number.

RailTest behaviour
cardSettles on confirm. Declines are not simulated yet; the fixture set comes with the issuer.
achSettles on confirm. Returns and NOC codes come with the sponsor.
instantSettles on confirm; the fee is the real 25¢.
POST

Create a payment intent

/v1/payment_intents

An intent is one attempt to collect a known amount. It carries the rail, the entity it belongs to, and the fee that will be charged if it settles.

ParameterTypeWhat it is
amount requiredintegerThe amount in cents. 250000 is $2,500.00 — never a decimal.
entity requiredstringThe entity the money belongs to, e.g. ent_ascot42.
railenumcard, ach or instant. Default card.
currencystringusd only in test mode.
descriptionstringWhat the payment is for; it travels to the statement and the event.
interchange_bpsintegerCard only. The interchange the card carries; default 224. The fee is computed from it and returned.

Confirm

/v1/payment_intents/{id}/confirm

Confirming settles the intent in test mode and creates a charge with the fee and the net. Confirming twice is 409 already_confirmed — never a second charge.

Request
curl -X POST https://api.ascotvale.app/v1/payment_intents/pi_7f3c1e0b9a4d2c81/confirm \
  -H "Authorization: Bearer $ASCOT_VALE_KEY" \
  -H "Idempotency-Key: confirm-8841"
200 OKthe intent now carries its charge

Refunds

/v1/refunds

Refund a charge in full or in part. The remaining balance is computed from the refunds already against that charge, so three partial refunds can never add up to more than the charge.

ParameterTypeWhat it is
charge requiredstringThe charge to refund, from a confirmed intent.
amountintegerCents. Omit for whatever is left on the charge.
reasonenumrequested_by_customer, duplicate, fraudulent, other.
Request
curl https://api.ascotvale.app/v1/refunds \
  -H "Authorization: Bearer $ASCOT_VALE_KEY" \
  -H "Idempotency-Key: refund-8841-a" \
  -d '{"charge":"ch_2a9d4e77b1c05f30","amount":40000,"reason":"requested_by_customer"}'
200 OK$400.00 of $2,500.00 refunded

Payouts

/v1/payouts

Move money out to a bank or a card. An instant payout is 25¢ flat — the same price the account charges, not a percentage of what is being moved.

Webhook endpoints

/v1/webhook_endpoints

Register a URL and the events it wants. Every state change is recorded as an event and delivered to each subscribed endpoint, signed with that endpoint's own secret.

EventWhen it fires
payment_intent.createdAn intent is created, before any money moves.
payment_intent.succeededAn intent is confirmed and its charge exists.
charge.refundedA refund is recorded against a charge.
payout.paidA payout leaves with its fee and net.
A dead endpoint never fails a payment. A delivery that errors is recorded on the event with the error, and the intent still succeeds.

Verifying a signature

The header is t=<unix>,v1=<hmac>, where the HMAC is SHA-256 over t.payload with the endpoint's secret. Verify it, and reject a timestamp older than five minutes so a captured body cannot be replayed.

Python
import hashlib, hmac, time

def verify(payload: str, header: str, secret: str, tolerance: int = 300) -> bool:
    parts = dict(item.split("=", 1) for item in header.split(","))
    stamp, given = int(parts["t"]), parts["v1"]
    if abs(time.time() - stamp) > tolerance:
        return False
    expected = hmac.new(secret.encode(), f"{stamp}.{payload}".encode(), hashlib.sha256).hexdigest()
    return hmac.compare_digest(given, expected)

Errors

One shape for every failure, so a client has one branch to write.

Error body
{ "error": {
  "code": "refund_exceeds_charge",
  "message": "That refund is more than what is left on the charge.",
  "hint": "$21.00 remains refundable."
}}
StatusCodeWhat to do
400invalid_requestThe body is wrong; the message names the field and what it expected.
400idempotency_key_requiredSend an Idempotency-Key on every write.
400refund_exceeds_chargeRefund less than the hint says is left.
401invalid_api_keyNo usable bearer key.
404not_foundWrong id, or the id belongs to the other mode.
409already_confirmedThe intent is not processing; read it instead of confirming again.
501live_mode_unavailableLive mode waits on the partner bank. Use a test key.

Rate limits

Test mode answers 120 requests a minute per key. A limit response is the same error shape with 429 rate_limited and a Retry-After header. Limits on the live service are set with the acquiring partner.

Nothing here is a promise of a processing licence. Ascot Vale is a financial technology company, not a bank; the sandbox exists so the API can be built and reviewed before the partner route is signed.
